# AGENTS.md - Jail Call Service Context

Codebase context for AI coding agents working on `jail-call-service`
([github.com/nathanjeichert/jail-call-service](https://github.com/nathanjeichert/jail-call-service)).
Read this before changing anything; update it when you change the architecture.

* **What it is:** a local-first batch tool that turns folders of G.729 jail call recordings (thousands per job) into a delivery zip: per-call transcript PDFs, MP3 audio, one offline HTML page (searchable call index + synced audio viewer), a case report, and a user guide.
* **Who runs it:** the operator (Nathan) on a Mac. Deliveries are opened by attorneys on locked-down government machines with no network, so every client-facing artifact is a self-contained file that works from `file://`.
* **Repo hygiene:** single `main` branch. `test files/` holds real recordings and is gitignored; the repo is public, so never commit call data, job output, or `.env`.

**Tech stack:** FastAPI + SQLAlchemy/SQLite backend; Next.js 16 / React 19 / Tailwind 4 / TypeScript frontend (Node >= 20.9); ffmpeg CLI; Playwright headless Chromium for PDFs; AssemblyAI and google-genai SDKs; FluidAudio CoreML and mlx-lm for local engines; onnxruntime + numpy to embed search passages (the page runs the same ONNX model on ONNX Runtime Web). Install with `pip install -e ".[dev]"` (add `,local` for Gemma); `pyproject.toml` is the only dependency list.

**Import rules:** `config`, `prompts`, `models`, `formatting`, `engine_registry`, `call_dates` are leaves; `case_documents` imports only `config` and `models` (pypdf and python-docx lazily inside its extractors) and is read by `job_settings`, `server`, and `delivery.case_report` (which also imports `job_settings.extract_case_context`; `job_settings` imports nothing from `delivery`); `backend.search` imports only `config` and `models` (and `onnxruntime` lazily inside `Embedder`), and `delivery.search_index` is the one module that imports it. The fixed speaker labels (`OUTSIDE_PARTY_LABEL`, `AUTOMATED_SPEAKER`) live in `models` and are read by `pipeline`, `system_audio`, and `search.passages`. `summaries` may import `delivery.summary_layout` (it needs the page budget) but nothing else in `delivery`. `delivery.call_view` is the only delivery module that imports `summaries` and `transcript_layout`; the generators read views. `job_settings` imports the engine packages lazily inside functions. `pipeline` imports `delivery.*` lazily inside functions so the API server starts without Playwright. Adding a top-level import that closes a cycle will show up as an ImportError on `import backend.server`; run the test suite after touching imports.

## Pipeline (`backend/pipeline.py`)

Assembly line: `[convert] -> [transcribe] -> [summarize] -> [pdf]`, four worker pools joined by asyncio queues, then a batch stage builds delivery assets and zips.

* **Stage runner.** Each stage is a `_Stage(name, job_stage, workers, process, on_error, queue, downstream)`. One `_worker` loop serves all four: pull an item, run `process`, emit a `call_update` event, forward the result downstream. `on_error` is the per-stage failure policy: conversion/transcription/PDF failures mark the call `ERROR` and stop it; a summarization failure is a soft failure (placeholder summary, `error` set, call continues to the PDF stage). Sentinels released by an upstream stage tell the downstream pool to drain.
* **Worker counts.** Conversion = CPU count - 1 (thread pool); transcription/summarization from `job_settings.RuntimeSelection` (`MAX_TRANSCRIPTION_CONCURRENT` / `MAX_SUMMARIZATION_CONCURRENT`, default 50, tuned to AssemblyAI's 100 new streams/min and Gemini Flash Tier 1's 300 RPM; local engines cap at `MAX_PARAKEET_CONCURRENT`=2 and 1 for Gemma); PDF = min(8, calls). All-local jobs (Parakeet + Gemma) run in two phases so both models never share unified memory.
* **Resumability.** Every stage transition is checkpointed via `job_store.update_call`. `_run_pipeline` routes each call into the queue matching its stored `CallStatus`, keyed by `original_path`, so pause/resume/crash recovery never re-spends API credits. **Resume the same job id; do not re-upload.** Pausing is cooperative: workers poll `job_store.get_job_stage` between items. `job_store.pause_orphaned_jobs()` runs at server startup so a job killed mid-run shows as paused, not running.
* **Validation up front.** `validate_runtime_selection` raises before any conversion if a selected cloud engine's key is missing or an engine is unavailable.
* **Engines are created once per run** and passed into the stages; the summarization engine stays loaded through case-report synthesis, then `unload()` frees local model memory.
* **Call records** (`_init_calls`): one `CallResult` per discovered file, with the ICM metadata copied by `asdict` when the report has a matching record and the date fields read from the filename otherwise (see "Job metadata & ICM XML").
* **Delivery assets** (`_stage_generate_delivery_assets`): builds one `CallView` per completed call (`delivery/call_view.build_call_views`: summary parsed, cues hydrated, page:line layout computed, filenames derived, once), then writes index.html, guide.pdf, case-report.pdf, and the `app-assets/` indexes (`delivery/search_index.generate_search_index`; `search_related=False` skips the related-words table, which the golden test does) in parallel threads from the same views; a failed asset emits a warning and does not fail the job. The PDF stage (`_generate_pdf_one`) builds a view per call and renders both transcript variants from it. `gen_date` overrides the "Generated" stamp (tests pin it); production leaves it as today. `_stage_package` zips `output/` as `<SafeCaseName>/...`. `repackage_job` re-runs both after summary edits, re-creating the same summarization engine the job used.
* **Events** (`backend/events.py`): thread-safe bounded queue per job; `server.job_events` streams it as SSE with 30 s pings. The frontend reloads the job on every event and falls back to 3 s polling.
* **Speaker labels.** `_build_channel_labels`: channel 1 (left) = inmate by default; the job's `speaker_assignment` (`left_inmate` / `right_inmate`) swaps sides. The inmate label is the ICM inmate name, else the job's defendant name, else `INMATE`; the transcript cover uses the same fallback.

## Persistence (`backend/job_store.py`, `backend/db.py`)

SQLite at `jobs/jail_calls.db` with WAL mode and a 30 s busy timeout for concurrent writers. `job_store` maps rows to pydantic models generically from the table columns (add a column to `db.py` and it flows through; `_ensure_schema()` adds missing columns to older local databases at import). A call's summary is stored twice: `summary` (the canonical text, still what the transcript PDF's summary sheet and the review textarea use) and `summary_json` (its structured twin from `summaries.build_summary_json`: the normalized `SummaryResponse` fields plus the parsed `review_cue_items`; `None` for skip-summary dummies, soft-failed placeholders, free text, and jobs from before the column existed). Both are written together at summarize time and by `PUT /api/jobs/{id}/calls/{i}/summary`, which normalizes the operator's text and rebuilds the JSON from what it stores, so the two never drift. Prefer the narrow readers: `get_job_lite` / `list_jobs` skip the transcript JSON, `get_call` loads one call, `get_job` loads everything. Per-job files live in `jobs/<id>/` (`output/` is what gets zipped; `source-working/` holds repaired copies of the source audio so originals are never mutated).

## Engine registries (`backend/engine_registry.py`)

Each stage package exposes `REGISTRY`, an `EngineRegistry` of `EngineSpec`s: `id`, UI `label`, `local`, `installed()` (dependency present), `requirement()` (None when it can run now, else the missing key/binary as a sentence), `create(**kw)`, `install_hint`, and `max_concurrency` for local models. `describe()` feeds `GET /api/config` (`transcription_engines` / `summarization_engines`, each row `{id, label, local, installed, ready, requirement}`); the frontend renders the menu and any "not ready" warning from those rows and names no engine itself. `job_settings.RuntimeSelection` reads `local` and `max_concurrency` from the spec; `validate_runtime_selection` raises the spec's `requirement`. **Adding an engine = write its module and add one `EngineSpec` to the stage's `REGISTRY`.** Nothing else in the backend or UI should name an engine. `tests/test_engine_registry.py` covers the shape, readiness, and validation with fake registries.

## Transcription engines (`backend/transcription/`)

`get_engine(name)` (= `REGISTRY.create`) returns an object with `async transcribe(audio_path, channel_labels) -> List[TranscriptTurn]`. Both engines return the same shape: ordered turns with `speaker`, `text`, `timestamp` (`[MM:SS]`), optional word-level `words` (ms), and `is_continuation` (same speaker as previous turn).

* **AssemblyAI (cloud):** stereo MP3 in, `multichannel=True`, submit-then-poll bounded by `ASSEMBLYAI_TRANSCRIPTION_TIMEOUT_SEC` (900 s; a stuck transcript raises `TimeoutError` and errors only that call). No `prompt` parameter (it caused spurious `[SPEAKER]` tags).
* **Parakeet (local):** splits stereo into two 16 kHz mono WAVs with ffmpeg, runs `bin/fluidaudiocli` (CoreML, gitignored ~7 MB; models download to `~/Library/Application Support/FluidAudio/Models` on first use) per channel, segments each word stream on 1.5 s gaps, and interleaves the segments by start time. Turn merging is simple; see `todo.md` item 5.

## Summarization engines (`backend/summarization/`)

Every engine subclasses `SummarizationEngine` (`base.py`); the pipeline and case report only use that interface. Three async operations, each returning its result plus `TokenUsage`:

* `detect_system_audio(turns, metadata)` — only when `system_audio_prepass = True` (Gemini). Runs before summarization so the summary sees a filtered transcript.
* `summarize_call(turns, prompt, metadata, *, detect_system_audio)` — returns `CallSummary` with either `structured` (a `SummaryResponse`) or `text` (raw model output). Inline-detecting engines (Gemma) fold detection into this one call and return `system_audio_markers`.
* `synthesize_case_report(CaseReportInputs)` — findings + outside-party identities as `CaseReportResponse`.

`pipeline._summarize_with_engine` is the only place that sequences these (prepass filter → summarize → post-filter for inline engines → normalize), and `delivery/case_report._run_synthesis` is the only caller of synthesis (3-attempt tenacity retry, 120 s per-attempt timeout). **Adding an engine = subclass the ABC and add an `EngineSpec` to `summarization.REGISTRY` (see "Engine registries"). Nothing in the pipeline or delivery code should branch on engine type.** `tests/test_summarize_stage.py` drives the stage with fake engines of both shapes.

* **Gemini** (`gemini_engine.py`, prompts in `json_protocol.py`): `gemini-3-flash-preview`; native JSON output against the pydantic schemas in `schemas.py`; `thinkingLevel` low for detection, medium for summary and synthesis (`GEMINI_*_THINKING_LEVEL`). Summary notes carry only `line_ref` + `reason` + `importance_rank`; every rendered timestamp, speaker, and pull quote is derived from the cited transcript lines (`transcript_layout.hydrate_review_cues`), never model-authored text.
* **Gemma** (`gemma_engine.py`, prompts + parsers in `text_protocol.py`): Gemma 4 E2B 4-bit via mlx-lm; lazy load with a warm-up pass, `unload()` after the run; strips the `<|channel>thought…<channel|>` reasoning prelude and raises if the budget ran out mid-thinking (recorded as a partial failure rather than saving reasoning as the summary). Case-report output is `FINDING_START…FINDING_END` / `IDENTITY_START…IDENTITY_END` blocks parsed into the same schemas. Local-only mode is parked (`todo.md` item 6).

**Summary shape** (`backend/prompts.py`): `RELEVANCE: HIGH/MEDIUM/LOW`; `NOTES:` timestamped attorney-relevant moments only or exactly `NOTES: NONE`; `IDENTITY OF OUTSIDE PARTY:` only when supported; `BRIEF SUMMARY:` one or two sentences. Do not make the model add notes merely to orient the reader to routine conversation. Prefer colons over em dashes in prompts and template copy.

**Normalization** (`backend/summaries.py`): before persistence every summary becomes the canonical text format: leaked preambles stripped, notes capped by tier (`SUMMARY_NOTE_GUIDANCE`, hard max 21), duplicates and weak notes dropped by importance rank, identity/brief text shortened to card length, and the kept note set reduced until it fits the summary-sheet page budget (`SUMMARY_PAGE_LIMITS`, via `delivery/summary_layout.paginate_structured_summary`). Beside the text, `summaries.build_summary_json` produces the JSON twin for every structured summary (Gemini's normalized response keeps its importance ranks; Gemma's text goes text → parsed → structured, so its ranks are cue order). All delivery surfaces read summaries through `delivery/call_view.build_call_view`, which prefers `summary_json` (`summaries.sections_from_summary_json` rebuilds the parser's shape, including the raw NOTES body the case report feeds to synthesis) and falls back to `summaries.parse_summary_sections` on the text for older jobs (the parser also accepts older REVIEW CUES / KEY FINDINGS formats). `tests/test_summary_json.py` pins that a view built from the JSON equals one built from the text; the synthetic package writes text only, so the golden exercises the fallback path. `DUMMY_SUMMARY_PREFIX` marks skip-summary test output, which the surfaces treat as "no summary" regardless of any JSON.

## Automated messages (`backend/system_audio.py`)

Provider IVR prompts, time warnings, and sign-offs play into both channels, so they appear on both speakers' turns. Engines return markers `{"turn": int, "text": str}` (Gemini: separate prepass on the raw turn transcript; Gemma: `SYSTEM_AUDIO: [...]` tail parsed by `text_protocol.parse_system_audio_response`). The job's `auto_message_mode` decides what happens: `None`/"Keep" leaves turns alone; `"exclude"` removes the system text (splitting mixed turns); `"label"` relabels it as speaker `AUTOMATED MESSAGE`, collapsing both channel copies into one turn. Default in the UI/API is `"label"`. Filtering only runs when summarization is active; `remove_system_audio_notes` also drops NOTES bullets that merely restate a detected message. Matching is fuzzy on purpose (a note is dropped when it contains the message or shares two or more content words within 3 s of it). A deterministic, model-free preamble pass is parked as `todo.md` item 4.

## Job metadata & ICM XML

Per-call metadata (inmate name/PIN, outside number, date/time, housing unit, outcome, call type) comes from the provider's `ICM_report.xml` via `backend/icm_parser.py`, matched to audio by `<recordfilename>`; `CallMeta`'s fields are named identically to `CallResult`'s so the pipeline copies them with `asdict`. Case-level metadata (case name, defendant, case context) is operator-entered. `POST /api/upload/xml` and `/api/xml/preview` return a parsed preview the UI shows and uses to prefill the defendant name.

**Case documents.** The operator can attach a complaint, police report, or other PDF / `.docx` / `.txt` / `.md` files to a job (`POST /api/upload/documents` for uploads, `POST /api/documents/preview` for pasted paths; both return name, path, page count, char count, and a 200-character preview). `case_documents.extract_document_text` converts each file to normalized text once at job creation (pypdf for PDFs with the page count, python-docx for Word paragraphs and table cells, UTF-8 for text; legacy `.doc` and scanned PDFs are refused with an operator-facing `ValueError` that the server returns as a 400) and the result is stored on the job as `Job.case_documents` (`DBJob.case_documents`, JSON, list of `CaseDocument` = name, path, text, pages). The text reaches two prompts and nothing else: `job_settings.effective_summary_prompt(job)` appends `case_documents.build_case_documents_block` to the stored `summary_prompt` for the per-call summarizer (the pipeline's summarize stage is the only caller), and `delivery/case_report._build_case_context` appends the same block after the operator's typed context (`extract_case_context(job.summary_prompt)`, never the whole per-call prompt) for synthesis. The block is `CASE DOCUMENTS:`, one instruction line telling the model the documents are context and never something said on a call, then `=== <name> (<N> pages) ===` and the text per document, with the concatenated text capped at `config.MAX_CASE_DOCUMENT_CHARS` (`MAX_CASE_DOCUMENT_CHARS`, default 120000) and a `[... truncated: ...]` marker when cut. The document text never enters `summary_prompt`, so re-runs (`GET /api/jobs/{id}/settings` returns `case_document_paths`) and the job list (`case_documents` as name/pages/chars only) see just what the operator typed; the delivery artifacts never carry document text. **No ICM record, no date:** `pipeline._init_calls` then fills `call_date` / `call_time` / `call_datetime_str` from the filename via `backend/call_dates.py` (a leading Unix epoch, as GTL names its files, rendered in the operator machine's local time, or `YYYYMMDD[_HHMMSS]`); nothing else is inferred, and an unrecognized name leaves the call undated. Every date-driven surface (the page's date filter, calendar, and timeline, the case report's timeline) reads those three fields and must cope with undated calls.

## Alignment: page:line is one computation

`backend/transcript_layout.compute_line_entries(turns, duration)` is the **single source of truth** for how transcript text wraps into 62-character lines and 25-line pages. It feeds:

* the transcript PDF sheets (`delivery/transcript_pdf.py`),
* `index.html`'s printed transcript pages and its full-text search (the page embeds each call's line entries once and re-derives speaker turns from them),
* every `Tr. page:line` cite in `index.html` and the case report,
* the `[Page:Line]` references the summarization prompt asks the model to cite (`summarization/base.build_transcript_text`), which later resolve back to lines, timestamps, and pull quotes via `resolve_line_ref_context` / `hydrate_review_cues`. A pull quote is the cited lines' text (up to 3 lines / 220 chars, ellipses when it starts or stops mid-sentence); one that stops mid-sentence at the end of the cite is carried to the end of that sentence on the same turn's next lines (`quote_for_line_cite`, at most 2 extra lines, still within 220 chars), so notes read as sentences rather than wrapped-line fragments.

`MAX_LINE_CHARS = 62` is pinned there; `delivery/transcript_pdf.py` asserts at import that its ruled-corridor geometry still yields 62 columns. **Changing the wrapping rules shifts every citation in the product.** `create_pdf` asserts the rendered page count equals the emitted sheet count and refuses to deliver on mismatch.

## Delivery artifacts (`backend/delivery/`)

Every generator takes the `CallView` list the delivery stage built (`call_view.py`): `view.call` (the `CallResult`), `stem` / `audio_filename` / `pdf_filename`, `line_entries`, `summary` (stored text) with `is_dummy`, `sections` (parsed) with `structured` / `relevance` / `brief` / `identity`, and `cues` (hydrated dicts with `timestamp`, `speaker`, `quote`, `note`, `line_cite`, plus `seconds` and `page`). Parse or lay a call out anywhere else and the surfaces can drift; add a derived field to the view instead.

All four templates are Jinja (`templates.render_template`, `autoescape=False`: pass pre-escaped strings and `html_json.dump_script_safe_json` output). All PDFs are Jinja HTML rendered by headless Chromium via `pdf_render.render_pdf(html, *, paged=False)`: a thread-safe sync facade over async Playwright on a dedicated daemon thread (one shared browser, fresh context per render, semaphore-gated, single relaunch-and-retry on crash). Setup: `python -m playwright install chromium` once. `paged=True` injects the vendored Paged.js polyfill for `@page` margin boxes, running footers, and page counters (case report only); `paged=False` prints explicit fixed-size sheets (transcript, guide).

* **Transcript PDF** (`transcript_pdf.py`, `templates/transcript_pdf.html`): cover sheet, summary sheet(s), then legal-deposition transcript sheets (Courier Prime, line numbers, double-rule corridor, 25 lines/page). Every page is an explicit `8.5in x 11in` sheet with `overflow: hidden`; Python decides all pagination. Summary pagination is height-based (`summary_layout.py`: measured advance widths in `font_metrics.py` times a 1.06 safety factor); identity and brief summary stay on page 1, overflow pages carry notes only, cap 3 summary pages. If you edit the summary layout, update both the estimator and the CSS: an under-estimate clips content inside the fixed sheet. Visually verify with `pdftoppm` before calling it done.
* **Case report** (`case_report.py`, `templates/case_report.html`, Paged.js): parses every summary once, buckets by relevance, selects synthesis inputs (HIGH first, topping up from MEDIUM to `TARGET_FINDINGS_INPUT_COUNT`=10), runs one synthesis call (findings + identities), then renders at-a-glance metrics, an adaptive-granularity call timeline (day/week/month/year by span; inline SVG precomputed in `_build_timeline_svg`), top findings, HIGH call cards, MEDIUM rows, and caller stats with inferred identities. `synthesis_state` (`ok` / `no_input` / `synth_unavailable` / `parse_failed`) drives a differentiated empty state so a failed synthesis still yields a usable report. **Link portability:** hrefs are relative (`index.html#call=…&t=…` from `_viewer_link`, `transcripts/<stem>.pdf`); Chromium bakes them as absolute `file:///tmp/...`, so `_rewrite_local_links` (pypdf, cloning the document so the contents page's named destinations survive) strips them back to `./`-relative `/URI` actions (`./index.html#call=…`, `./transcripts/<stem>.pdf#page=N`), the one form Chromium's viewer (Edge, the client reader) follows: it resolves them against the PDF and honors both fragments, but fixes a bare `index.html#…` up as a hostname, jumps *within the report* on a `/GoToR`, and a `/Launch` hands the fragment to the reader as part of a filename. macOS Preview follows only the contents links (`tests/test_case_report_links.py`; verified by clicking in both readers 2026-09-10). Every `#page=` in the delivery is a physical page: the page's `pdfUrl` and `_finding_sources` add the call's `CallView.pdf_front_matter_pages` (cover plus summary sheets) to the printed transcript page. Paged.js does not replicate `position: fixed` per page: per-page chrome is styled on `.pagedjs_page`. The call card's lead block (`.cc-lead`: header, brief, outside party, and the viewer/PDF links) is unbreakable and the cue table flows across pages by row; the card itself has no `page-break-inside: avoid`, and nothing uses `page-break-before: avoid` (Paged.js honors it by pushing the preceding content to the next page, which once left a card header alone on an otherwise empty page). Dry-run a job and eyeball the PDF after template edits.
* **Guide** (`guide_pdf.py`, `templates/guide.html`): 7 fixed sheets (cover, contents, the index view, calendar and timeline, the call view, the case report, reading the analysis); screenshot PNGs in `assets/guide/` (`index_view_screenshot.png` and `call_view_screenshot.png` at 1600x1040; `calendar_view_screenshot.png` and `timeline_view_screenshot.png` at 1600x760, shown side by side) are synthetic ("State v. Marcus Reeves"), safe to ship, and regenerated from the synthetic package with `python tests/render_guide_screenshots.py` after any visual change to index.html; missing PNGs render as dashed placeholders, so keep them present. Copy is usage information only, no review-order advice (client preference). `tests/test_guide_layout.py` pins the page count and footer tokens.
* **Index page** (`index_html.py`, `templates/index.html`): the one HTML deliverable, self-contained, two views switched by the URL hash. `#index` (or no hash) is the call index, the client's home page: masthead stats, a sticky two-row filter bar (the search box with the Smart search / Exact words only switch; then the Said-by chips, date range, number, outcome, and length menus with call counts, relevance chips and the clickable tally), one row per call with relevance marker and, during a search, the matched passages with their match tags (see "Search"), expandable summary/cues/full transcript with match stepping, Viewer/PDF buttons. `#calendar` and `#timeline` are the index's two chart modes (the List / Calendar / Timeline switch in the tally row, offered only when some call has a date; a chart hash falls back to the list otherwise): the same filtered set drawn by `templates/index_charts.js`, a Jinja include that lands inside the page's IIFE and defines `Charts` (`calendar`, `timeline`, `extent`, `maxPerDay`, `buildBuckets`, `granularity`). The frame is fixed to the span of every dated call (`Data.dateExtent`), so filters change the marks, never the months or the axis. The calendar tints each day against the unfiltered busiest day (`Data.maxPerDay`, so the legend holds), shows a span of up to twelve months whole and a longer one a year at a time (only the months the span covers; the year lives in `IndexView.state.calYear`). The timeline buckets by day / 7-day week / calendar month / calendar year at the same thresholds as `case_report._build_timeline` (60 / 392 / 1860 days; the browser test pins the agreement), draws calls per bucket as columns with HIGH in crimson over the neutral tint, then a HIGH and a MEDIUM lane with one mark per bucket, and redraws on resize. A day, column, or lane-mark click calls `IndexView.showRange`, which sets the date filter (and the tier), switches to the list, and routes to `#index`; the other filters stay. ## Search (`backend/search/`, `delivery/search_index.py`, `templates/index_search.js`)

The page's search is a BM25 keyword index over passages plus, when the package was built with the embedding model, a **related-words table** that is Smart search's meaning layer: every query word expands to the corpus words the model says mean the same (cop finds police, attorney finds lawyer), and the page marks the word it actually matched. Both are precomputed at delivery time and run in the page from `file://`; nothing runs a model in the browser. The design and the measurements behind every constant are in `docs/search-plan.md` (section 7 for why the meaning layer is word-level); the short version:

* **Passages** (`search/passages.py`): the unit both indexes score. Turn-aware windows of ~100 words with 50 % overlap over each call's `line_entries` (the same entries the page embeds), pointing at line ranges and carrying their `pieces` (text, speaker bits per line), which is all the index builder reads; plus one summary passage per call (`summary_text`: outside number, inmate, identity, facility, outcome, call type, brief, cue notes and quotes, joined with ` · `) so metadata and summaries are searchable. A summary passage carries every speaker bit (`SPEAKER_ANY`), so speaker filtering is one bitmask test in both engines and a summary hit survives any Said-by chip. `speaker_bit` classes lines: `OUTSIDE PARTY` and `AUTOMATED MESSAGE` are fixed labels, anything else is the defendant.
* **Tokenizer** (`search/tokenize.py`, ported line for line at the top of `index_search.js`): fold to lowercase ASCII, join phone-number digit groups (`(530) 555-0192`, `555-0192`, `5305550192` become one run, indexed with its last-7 and last-4 tails), expand a contraction table, split on non-alphanumerics, Porter-stem; `index_terms` drops stopwords and filler, `stem_tokens` keeps them for phrase matching. **Change the Python and the JS together**: `test_search_browser.py` asserts identical output over every synthetic transcript line.
* **Keyword index** (`search/lexical.py` -> `search/index.js`, `window.JCS_SEARCH`): sorted vocabulary, per-term postings as a varint byte stream (passage delta, tf, speaker bits), the passage table as typed arrays, all base64. `LexicalIndex.score` / `call_scores` are the Python reference of the page's rules: BM25 (k1 1.2, b 0.75) over every passage carrying any content term, calls ranked by their best passage (MaxP), Smart mode drops calls under `RELATIVE_CUTOFF` (0.3) of the top call, Exact words only needs every content term, quoted phrases are verified on the stemmed stream. The page adds prefix expansion for the last term while typing and edit-distance-1 typo tolerance for words of five letters or more (Smart only, never digits), and marks the vocabulary word it reached.
* **Related words** (`search/related.py`, `search/embeddings.py`, `search/assets.py`): at build time the surface words of the corpus (`corpus_words`, as spoken, mapped to their stem) and a fixed lexicon (`lexicon_words`: the ~20k whole alphabetic words of the model's own vocabulary, so a query word the transcripts never use still expands) are embedded one word at a time with `Embedder` (`EMBEDDING_MODELS` registry, `minilm-l6` = all-MiniLM-L6-v2 int8 ONNX, Apache-2.0; `WordPiece` is its tokenizer). `build_related` keeps, per query stem, the corpus stems whose word-to-word cosine is at least `RELATED_MIN` (0.62), strongest first, at most `RELATED_MAX` (6), never its own stem, as `{stem: [[vocab index, cosine*100]…]}`. Word-level is the point: mean-pooled passage vectors could not separate one "police" from the rest of a 100-word passage (measured: the best passage for "cop" scored 0.34, police passages below unrelated ones), while word cosines are clean (cop/police 0.68, attorney/lawyer 0.86, noise under ~0.5). The model and vocab are downloaded once by `python -m backend.search.assets` into `config.SEARCH_ASSETS_DIR` (`~/Library/Application Support/JailCallService/search`, `SEARCH_ASSETS_DIR` overrides), pinned by SHA-256, never committed; the lexicon's vectors are cached beside them (`<model>.lexicon.npz`). `delivery/search_index.generate_search_index` fetches the model at delivery time and ships keyword search without the table, with a warning, if it cannot. **Swapping the model** = one `EmbeddingSpec` entry (and the cache re-fills); nothing else names it.
* **Sidecar** (`search/build.py`): one file, `app-assets/index.js` (`window.JCS_SEARCH`): the passage table, vocabulary, and postings, plus `related` when built with the model. Classic `<script src>` files are the only data channel `file://` allows (no fetch, no modules, no file-path workers).
* **In the page** (`Search` in `index_search.js`): `index.js` is injected after first paint and search is live when it parses (`state.lexical` `ready`, `state.related` `ready` or `none`); a missing `index.js` (zip opened without extracting) falls back to the old substring search with an "extract the zip" notice (`state.lexical === 'missing'`). `parseQuery` gives each content term its expansions into the vocabulary: the term itself, else (Smart only) its typo/prefix neighbours at `FUZZY_WEIGHT` 0.7, plus (Smart only, never inside a quoted phrase) its related words weighted by cosine. In `lexicalScores` every expansion of one query word shares that word's slot: a passage takes its best-scoring expansion, and a word the passage holds itself keeps the slot exact even when a related word scores higher. A passage's result carries `matched` (query words it holds itself) and `related` (those it holds only through a related word); Smart mode needs one of either, Exact words only needs every word itself, and phrase words must be held itself. Calls rank by their best passage (MaxP), cut below `LEXICAL_CUTOFF` (0.3) of the top call in Smart mode. `Search.query(text, {smart, speakers})` returns `{calls: Map(call index -> {score, evidence})}` (memoized per query, so paging and row toggles re-render for free). Evidence items carry a match category (`phrase` / `words` / `partial` / `related`) plus `matched` / `related` / `needed`; the view's `badgeFor` turns that into the tag (`Exact words` / `Exact phrase` / `N of M words`, with ` + related` appended when related words also hit, or `Related words` when only related words hit; the related tag, the related `<mark>`, and a related-only passage are dashed via the design layer's `.is-related`). `Search.evidence(item, matcher)` gives the anchor and snippet (the line carrying most of the query's words, related ones included, a window around its first marked word). `Search.matcher` is the one highlighter the rows, the detail panel, and the call view's transcript search share; its `hit(word)` returns `''` / `'exact'` / `'related'` and is memoized per query. `Search.relatedWords(stem)` exposes the table for the tests. Constants were tuned on the demo corpus (`docs/search-plan.md`); keyword evidence leads by design, per the product owner.
* **UI state** (`IndexView.state`): `smart` (the Smart search / Exact words only switch, prominent beside the box), `speakers` (Said-by chips, inert without a query), `outcome`, `length`, and `sortKey: 'match'` (set when a query starts; ranks by match strength until a column heading is clicked, reads as date order without a query; the count says "best match first"). Recent searches live in `localStorage` `jcs_recent_searches` as a `datalist`, best effort.

## Offline attorney review (`index.html`)

`templates/index_review.js` owns the case-bound review store; `index_review_ui.js` owns its controls and pinned-notes presentation. Both are Jinja includes inside the existing ES2017 IIFE. `index_html.generate_index_html` embeds a SHA-256 fingerprint of the case name, ordered call filenames, durations, outside numbers, and transcript line entries, independently of generation date and summaries. Each cue carries a content-derived ID. Review data never changes transcript lines, generated summary text, PDFs, or search sidecars.

* **Direct file autosave:** the attorney clicks **Enable autosave**, selects the extracted delivery folder through `showDirectoryPicker({mode: 'readwrite'})`, and the page verifies the fingerprint in the first 1 KB of that folder's `index.html`. It creates or reconnects `case-review.json` there. No server, network, installation, admin permission, or manual export/import flow. Supporting desktop Edge/Chrome and ordinary write access are required; enterprise browser policy can deny access. An unsupported/denied API leaves an explicit browser-only/unsaved status, not a success claim.
* **Persistence:** version 1 JSON (`format: jcs-review`, `caseId`, `caseName`, `records`) holds only review fields. Records are keyed by call audio filename + field, cue ID, or normalized phone digits (a leading US country code is removed). Each value has a logical millisecond clock and random actor ID. Merge per field by clock then actor; false, empty string, and null resets are retained so old backups cannot resurrect removals. Preserve orphaned cue pins on summary-only repackaging, but do not display them against different notes. Reject wrong-case, unknown-version, malformed, oversized, and invalid-field files before writing.
* **Recovery:** `localStorage` `jcs_review_<caseId>` is a synchronous best-effort redundant copy. IndexedDB `jcs-review-handles` stores directory handles by case ID; on opening, read the browser copy, restore the handle, and automatically reconnect only when permission is already granted. Otherwise a user gesture reconnects it; selecting the folder again works after moving the package or clearing browser storage. The UI distinguishes disk saving, browser-only recovery, unavailable backup, and failure. Writes debounce 350 ms, serialize, merge the latest disk version under a Web Lock when available, and commit via `createWritable`/`close`; failed writes retain the browser copy and require reconnect. Pending writes warn on unload. This is an individual review workspace, not simultaneous multi-user collaboration across browsers/computers.
* **Review fields:** star/unstar, reviewed/unreviewed, relevance override (empty resets to original), default name per phone number, nullable per-call name override (`null` uses the number default; empty deliberately suppresses it), and pin/unpin of existing generated notes. `ReviewUI` applies derived presentation fields to calls without mutating source transcript/summary content. Relevance feeds existing sorting, tallies, filters, calendar, and timeline. Stars/review status filter every index mode; names appear in headings, number menus, and chart tooltips and are matched as additional metadata in index searches.
* **Pinned notes:** `#notes` is a fourth index mode, available even without dates. It shares index filters and shows 50 pins per page, with generated note text, source quote, call/number identity, transcript cite, and viewer/PDF links. Pin controls never also seek audio or expand rows.
* **Automatic review:** on native audio `ended`, require actual `audio.played` coverage with no more than `min(5 seconds, 2% of duration)` unplayed. Coverage is for the current loaded recording; merely seeking to the end does not count. A stored manual reviewed/unreviewed choice takes precedence. Review control edits refresh presentation without restarting audio or rerendering transcript sheets, and text controls/dialogs suppress player keyboard shortcuts.
* **Tests:** `tests/test_review_browser.py` exercises the UI and storage contract from `file://`, using a file-handle double with staged writes and real IndexedDB transactions (a serializable stand-in represents the native handle). It covers reconnect, disk/cache merges, tombstones, write failure, edits during a write, invalid files, blocked browser backup, name overrides, chart/filter propagation, pins, and playback coverage. Native OS folder-picker permission UI and restart behavior on managed Windows browsers require separate manual verification.
